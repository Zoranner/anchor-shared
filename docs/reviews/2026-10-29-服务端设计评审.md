# Anchor Guard 服务端设计评审报告

## 评审范围

本次只评审服务端管理模式的设计完整性、架构边界、安全信任关系、实施计划和工程可验证性，不评价具体功能是否已经实现，也不把尚未编写的代码当成缺陷。

用户已确认本期服务端不保存审计数据，审计日志只在客户端本地查看；本报告不把“服务端没有审计链路”列为问题。

用户已确认设备认证采用“服务端随机令牌 + 管理员审批”，不做机器指纹硬绑定；本报告只评审令牌生命周期和审批边界。

评审对象：

- `docs/superpowers/specs/2026-10-29-anchor-guard-server-design.md`
- `docs/superpowers/plans/2026-10-29-anchor-guard-server.md`
- `docs/design.md`
- `.github/workflows/release.yml`
- 当前仓库的目录和构建入口

## 评审依据

- `review-engineering` 通用工程基线和 Rust、Nuxt 专项清单。
- 当前仓库的 `AGENTS.md`、`Cargo.toml`、现有客户端 crate 边界和发布工作流。
- 用户已确认的目录规则：根 `crates/` 只放服务端和客户端共享的 crate；客户端专用 crate 放 `client/crates/`；服务端专用 crate 需要时才放 `server/crates/`。
- 用户已确认的数据库选择：SeaORM 2.0.2，底层使用 `sqlx-postgres`；schema 初始化代码放 `server/src/schema/`，不建独立 SQL 迁移目录。

## 总体结论

方向成立，核心信任模型清楚：服务端负责签名，客户端本地验签并保留最终授权判断，服务端不可用时保留缓存和离线导入；注册审批、全量硬件清单、可视化策略编辑和密钥轮换也都进入了设计。

当前还不是可以直接进入实现的完善状态。主要缺口集中在三条主链路上：

1. 设备令牌的签发、重试、轮换和撤销流程没有完全定死。
2. 服务端签名密钥的信任建立和轮换没有闭合。
3. 策略版本、分配、校验和离线签发的责任边界没有定完。

数据库表名、字段名和 API 契约已在本轮补齐，剩余工作是把它们落成 SeaORM 实体、OpenAPI 和测试。

## 主要问题

### 设备令牌生命周期仍有未定项

**定性：** 规范缺失导致的高风险。

**依据：**

- 设计已定义注册返回令牌、Bearer 使用和 `pending` 重试（设计文档 `:53`、`:161-166`），但没有定义 token 哈希算法、常量时间比较、`reset-token` 后客户端如何重新取得令牌和待审批设备配额。
- 计划只列出 `ServerSyncConfig { base_url, device_token, server_public_key }`（计划 `:582`）和 `register/status/heartbeat/fetch_policy`（`:583`），没有把 Bearer 请求头、401/403 语义和令牌轮换写进客户端契约。
- 注册接口虽然是匿名的（计划 `:418`），设计已要求按 IP 和 `installation_id` 限流，但没有给出具体阈值和拒绝策略。

**风险：**

设备令牌如果只作为普通 Bearer 值传输，泄露后可以重放心跳和策略拉取；匿名注册可以被批量刷入待审批列表，造成管理台和数据库压力。客户端实现时也没有明确依据判断 401、403 和令牌失效。

**建议：**

采用服务端生成的 256 位随机令牌：注册成功时只返回一次，服务端保存哈希，客户端保存在 ACL 保护文件中；后续请求使用 `Authorization: Bearer <token>`，令牌只经 HTTPS 传输。管理员审批作为唯一准入条件；补充令牌轮换、撤销、丢失后重新注册、注册限流和待审批设备配额。当前威胁模型不需要设备密钥对或机器指纹硬绑定；DPAPI 仅作为可选离线保护。若以后需要请求级防重放，再在令牌基础上增加 nonce 或改为签名认证。

### 服务端签名密钥的信任建立与轮换未闭合

**定性：** 规范缺失导致的高风险。

**依据：**

- 服务端持有策略签名私钥（设计文档 `:48`），客户端注册获批后才获得验证公钥（`:53`）。
- 设计没有说明客户端如何确认这个公钥属于当前服务端，也没有说明证书信任、公钥固定或密钥元数据签名。
- 密钥轮换要求“已安装客户端需要使用新服务端密钥重新安装”（`:153`），但没有定义新旧密钥并行期、`server_key_id` 校验、旧客户端如何判断密钥已撤销。
- 计划只在 `PolicyEnvelope` 中放了 `server_key_id`（计划 `:127-129`），没有对应验证和轮换流程。

**风险：**

如果服务端或 HTTPS 通道被替换，客户端可能接受攻击者下发的验证公钥；轮换时旧客户端可能直接失效，或者继续接受已撤销的旧密钥。重新安装全部客户端也不是可接受的日常运维路径。

**建议：**

定义密钥元数据（`key_id`、公钥、生效时间、失效时间、状态）和签名关系；客户端固定当前信任公钥，轮换时同时接受新旧密钥并带重叠期；策略包和密钥元数据都要能按 `server_key_id` 验证。明确旧密钥撤销和客户端迁移条件，不要把“重新安装”作为唯一轮换手段。

### 策略版本、分配、校验和离线签发边界未定

**定性：** 规范缺失导致的高风险。

**依据：**

- 设计规定策略版本在部署实例内单调递增（设计文档 `:101`），但计划只说“同一部署实例内版本严格递增”（计划 `:434`），没有说明版本由数据库序列、事务还是应用层分配，也没有说明并发签名时的冲突处理。
- 设备优先使用单设备分配，否则使用默认策略（设计文档 `:103`；计划 `:438`），但没有定义同时存在多条分配、默认策略被替换、分配删除后的回退规则。
- 服务端直接复用 `anchor-core` 的 `PolicyPayload` 和签名逻辑（计划 `:430`），但没有说明服务端是否复用现有 `anchor-policy` 的允许列表校验和正则校验。
- 服务端不可达时保留本地文件导入（设计文档 `:12`、`:113`），但现有 `admin/anchor-policy` 被标记为旧离线 CLI、本次不迁移（计划 `:35-36`）。服务端在线时由谁导出可离线导入的签名包也没有定义。

**风险：**

可能签出客户端拒绝的无效策略，或者多个管理员并发签名产生版本冲突；离线兜底在服务端不可达时可能没有可用签名工具。旧 CLI 和新服务端同时持有签名职责，也会造成密钥保管和签名口径分裂。

**建议：**

明确版本分配的唯一来源和事务边界；定义分配优先级和回退规则；服务端签名前复用现有策略校验，并补服务端校验测试；明确离线包的导出方式，或把旧 CLI 纳入服务端工具链并写清密钥保管、使用和废弃计划。

### 管理端认证和会话生命周期不完整

**定性：** 规范缺失导致的中风险。

**依据：**

- 计划要求 Argon2id、HttpOnly/Secure/SameSite Cookie 和 CSRF（计划 `:320-326`），但没有会话过期、会话轮换、登录失败限流、账户锁定、密码重置、管理员角色和反向代理信任边界。
- 设计只说“管理台只有管理员角色”（设计文档 `:49`），没有说明是否支持多个管理员、管理员被删除后的会话处理。

**风险：**

登录接口可能被暴力破解；会话 Cookie 被窃取后无法主动失效；初始化完成后缺少管理员恢复路径；多个管理员场景下的权限和会话口径不明确。

**建议：**

定义会话 TTL、滑动续期、登录限流和锁定策略；定义管理员角色、密码重置和会话撤销；明确反向代理下 `Secure` Cookie、客户端 IP 和 HTTPS 终止的信任规则；明确管理员会话撤销和权限变更。

### 部署、密钥注入和客户端 TLS 信任不足

**定性：** 规范缺失导致的中风险。

**依据：**

- 设计说私钥保存在宿主机 bind mount 或 Docker secret（设计文档 `:57`、`:233`），计划已改为 `server/deploy/app/data` 的 bind mount 和 `ANCHOR_MASTER_KEY_FILE`；仍需明确 Docker secret 注入方式。
- 计划已改为 `server/deploy/docker-compose.yml`，包含 PostgreSQL 16、健康检查和 bind mount（计划 `:282-338`）；仍缺反向代理/TLS、资源限制、备份恢复演练和 schema 初始化失败处理。
- 客户端只填写服务端地址和端口（设计文档 `:58-61`），设计要求 HTTPS 校验证书（`:51`），但没有说明内网自签名 CA 如何配置到客户端；若没有 CA 配置，客户端可能只能关闭证书校验或无法注册。

**风险：**

密钥可能以明文环境变量进入容器和日志；内网部署可能因证书信任失败而无法注册；数据库或 schema 初始化失败时缺少可恢复路径；备份不完整会同时丢失设备、硬件和策略数据。

**建议：**

明确 Docker secret 或受保护文件的注入方式，禁止把主密钥写入镜像、Compose 明文和日志；补充反向代理/TLS、资源限制、备份恢复和初始化失败处理；客户端增加 CA 证书或受控信任配置，并明确证书校验不可关闭。

### 计划中的目录迁移仍有旧路径

**定性：** 违反已确认的目录规范，属于中风险实现阻断。

**依据：**

- 计划 Task 1 要把 `runtime/` 改为 `client/`、`installer/` 改为 `client/installer/`（计划 `:111-120`），并明确更新 `.github/workflows/release.yml` 和 `docs/design.md`（`:121-125、187`）。
- 安装器任务已改为 `client/installer/AnchorGuard.wxs`、`client/desktop/...` 和 `git add client/installer`；计划路径已一致。
- 当前 `docs/design.md:213` 仍是 `runtime/desktop`；`.github/workflows/release.yml:49-64、122、139-141` 仍使用 `runtime/desktop`、`installer/`。

**风险：**

按计划执行目录迁移后，安装器构建和发布工作流会继续找旧路径，导致 MSI 构建失败；文档和实际目录也会漂移。

**建议：**

在 Task 1 执行后检索整个仓库，确认 `runtime/`、`installer/`、`server/admin/` 不再作为新路径出现；当前旧路径属于尚未执行的迁移，不是设计遗漏。

### 质量门禁和锁文件不完整

**定性：** 规范缺失导致的中风险。

**依据：**

- 管理台任务运行 `bun install --frozen-lockfile`（计划 `:551`），计划已列出创建 `server/web/bun.lock`（`:513`），但尚未实际创建。
- 服务端任务仍以 `cargo test -p anchor-server` 为主（计划 `:389`、`:445`、`:496`），需要在现有 release workflow 中补 fmt、clippy 和 schema 测试。
- 现有 `.github/workflows/release.yml` 的 verify 任务只覆盖客户端 Rust 和 `runtime/desktop`，没有 `server` 或 `server/web`；按用户要求只能在现有 release workflow 内扩展，不新增工作流。

**风险：**

`--frozen-lockfile` 会直接失败；服务端和 web 的质量门禁依赖个人手动执行；发布流程可能在服务端未验证的情况下继续构建 MSI。

**建议：**

提交 `server/web/bun.lock`；为服务端增加 fmt、clippy、test 和 schema 测试；把这些步骤加入现有 `.github/workflows/release.yml` 的 verify 流程，不新建 workflow；把服务端测试数据库的启动和清理纳入测试脚本。

### 客户端同步策略和硬件清单治理未量化

**定性：** 规范缺失导致的中风险。

**依据：**

- 设计说客户端按固定周期和网络变化拉取策略（设计文档 `:107`），但没有周期、抖动、超时、退避、网络变化检测方式、离线缓存过期判断和时钟偏差处理。
- 全量硬件清单包含序列号、MAC 地址、磁盘和 USB 标识（设计文档 `:75-87`），但没有采集频率、大小上限、保留期、脱敏或删除规则。

**风险：**

大量客户端同时轮询会造成服务端压力；断网恢复后可能重复请求；硬件标识属于敏感资产信息，长期无上限保存会增加隐私和数据库治理风险。

**建议：**

定义同步周期、抖动、超时和指数退避；明确网络变化事件和时钟偏差处理；为硬件快照定义大小上限、变更检测、保留期和敏感字段访问控制。

## 整改优先级建议

### P0：开始写服务端代码前必须定完

- 定义设备令牌签发、传输、哈希存储、轮换和撤销；补充注册限流，重放保护按需要再增加 nonce。
- 定义服务端签名密钥的信任建立、`server_key_id` 校验和轮换重叠期。
- 明确策略版本分配、分配优先级、服务端校验和离线签发方式。

### P1：首次部署前补齐

- 把已定义的 API 契约落成 OpenAPI、`anchor-protocol` DTO 和服务端校验。
- 定义管理员会话 TTL、登录限流、密码重置、角色和会话撤销。
- 补充 Docker secret、TLS/反向代理、备份恢复和初始化失败处理。
- 量化客户端同步周期、退避、超时和硬件快照治理。

### P2：实现和验收阶段同步完成

- 统一目录迁移后的所有文档、脚本和工作流路径。
- 增加 `server/web/bun.lock`、服务端 fmt/clippy/test、web lint/typecheck，并加入现有 release workflow 的 verify。
- 增加注册滥用、密钥轮换、数据库恢复和离线兜底的验收场景。
