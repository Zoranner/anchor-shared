# Anchor Guard 设计文档

## 项目定位

Anchor Guard 是部署在内部 Windows 10 笔记本上的本地终端管控与归还审计系统。管理员在固定管理电脑上离线签发策略包，策略内容描述设备端的行为规则而不是设备清单；笔记本从 U 盘导入策略，在本地执行网卡、USB 存储、刻录和文件风险识别规则，并将操作与异常保留在本机审计库中。

系统的授权状态同时决定 Windows 的正常登录和解锁是否可用。策略失效、缺失、审计完整性异常或授权状态无法确认时，登录页只保留策略导入入口；导入有效策略后才恢复 Windows 原有登录方式。

本设计服务于设备在授权期内可正常使用、到期后默认锁定、归还时可审计的目标。它不是对拥有本机管理员权限者的强制防护方案。

## 范围与边界

系统只面向 Windows 10 笔记本。服务、系统适配和 CLI 使用 Rust 实现，桌面端使用 Tauri 2、Nuxt 4 和 Vue；设备操作通过 Windows 设备安装接口（SetupAPI 与 CfgMgr32）直接读取和变更设备节点，不依赖 PowerShell、WMI 或脚本宿主。设备枚举只包含在场设备，不包括已移除的幽灵设备；被禁用的设备仍在观测范围内，因此策略放开后可以重新启用。

系统不包含以下职责：

- 服务端策略分发、自动内网更新、远程状态上报和远程审批。
- Linux 或其他平台适配。
- 文件写入前的内核级拦截、文件隔离和删除。
- 对本机管理员、恢复环境或离线磁盘修改的绝对防护。

U 盘只承担策略包传输职责，不是信任根。策略有效性由管理员签名、版本和有效期共同决定。

## 信任关系

服务端持有策略签名私钥，私钥使用主密钥派生的 AES-256-GCM 密钥加密后保存在数据目录。离线兜底使用管理台导出的已签名策略包，不在管理电脑保存第二套签名私钥。私钥不得写入笔记本、策略 U 盘或审计导出文件。

管理员通过服务端管理台签发策略。策略不包含设备清单：声明为 `deny` 的域由设备自行枚举本机设备并全部拒绝，只有需要为个别设备开例外时才在允许清单中填写设备实例标识。任何持有管理员公钥的设备都接受同一份策略，策略的适用范围由分发流程控制，而不是由策略内的设备标识控制。

策略可以完全锁死：签发不要求为任何设备开例外。介质类型不是安全边界，信任来自策略签名，因此导入通道不限于可移动盘，而是任意本地卷根目录下的固定文件名 `anchor-guard.policy`。

导入项只出现在授权不明或拒绝的登录页：无策略、策略过期或服务停止时，登录页保留导入项，此时可用任意本地卷（可移动盘、固定卷、光驱）投放新策略；授权有效时登录页只显示系统登录项，已登录用户可从桌面端提前导入新策略，导入仍由服务完成验签、版本比较和原子替换。

离线模式的本地配置只保存管理员公钥和一个本机审计标识。服务端模式的本地配置保存服务端地址和数据库路径，设备令牌和信任公钥由客户端安全存储；安装标识在首次启动时生成。拥有本机管理员权限的人可以修改本地文件，但这不影响服务端审批和签名策略的授权结论。

```text
服务端管理台
  策略配置 + 加密签名私钥
          |
          v
  导出已签名策略包
          |
          v
U 盘根目录的 anchor-guard.policy
          |
          v
Windows 10 笔记本
  验签、版本与有效期校验
          |
          v
本地策略执行、登录控制和审计
```

## 核心对象

系统保留以下具有独立生命周期的对象：

- 策略包：管理员签发的完整管控规则和授权有效期。
- 本地有效策略：笔记本当前已验证且处于有效期的策略包。
- 审计事件：本机追加写入的行为和异常记录，组成 hash chain。
- 扫描索引：已扫描文件的指纹、规则版本和命中摘要，用于增量风险识别。
- 设备状态：USB 存储、网卡和刻录设备的最近可观察状态。
- 运行状态：服务上次运行结果、最后可信时间和当前授权结论，用于启动恢复与时间回拨判断。

策略、审计事件和运行状态分别承担授权、追溯和运行恢复职责，不能互相替代。

## 策略包

策略包采用签名 JSON，管理员通过 TOML 配置生成。包中至少包含：

```text
version
expires_at
usb
network
burning
scan
signature
```

策略在导入时刻生效，不需要声明起始时间：导入动作本身会写入带时间戳的审计事件。`version` 在同一台设备上单调递增。导入只接受签名有效、版本不回退且尚未到期的包。验证失败时不得覆盖当前本地策略；无有效策略时设备保持登录拒绝状态。

策略使用默认拒绝模型：未被规则明确允许的受控操作不应可用。每一份策略包完整表达当前授权，不依赖本地审批令牌、策略合并或服务端补充状态。

授权状态判断遵循以下规则：

```text
存在已验签策略
且 当前时间 <= expires_at
且当前时间未超出允许的回拨容差
且审计链和运行状态可验证
        => 允许登录并执行策略

其余情况
        => 拒绝登录和解锁，仅允许导入策略
```

服务维护最后可信时间。系统时间向后回拨超过固定容差（当前为 300 秒）时，服务记录异常并进入拒绝状态；新的有效策略导入后重新建立授权状态。

## 登录与恢复

Windows 登录控制由两个 Rust COM `cdylib` 组件完成：

- Credential Provider：在拒绝状态提供“导入策略”登录项。
- `ICredentialProviderFilter`：在控制台登录和工作站解锁场景，根据授权状态动态过滤系统的密码、PIN、Windows Hello 等登录项。

Windows 服务是授权状态的唯一判断者。Credential Provider 和 Filter 通过本地 Named Pipe 向服务查询状态，不读取策略文件或 SQLite 数据库。查询超时、服务不可用、协议校验失败或状态不明时一律返回拒绝。

```text
策略有效
  -> Filter 放行 Windows 系统登录项
  -> 用户可按原有方式登录和解锁

策略失效、缺失或异常
  -> 服务返回拒绝状态；用户会话协作程序锁定当前交互会话
  -> Filter 仅放行 Anchor Guard 导入策略项
  -> 系统登录项不可见，普通用户无法登录或解锁
```

每个交互会话运行 `anchor-session` 协作程序。它只通过受限的只读状态管道查询服务，并在拒绝或服务不可用时调用 Windows 锁屏 API；它不保存策略、不做授权判断。服务处于 Session 0，不能将自身的 `LockWorkStation` 调用视为交互用户已锁定。

每个交互会话还运行一个托盘桌面端 `anchor-guard.exe`。桌面端通过 `AnchorGuard.Desktop` 管道查询授权、预览和导入策略，并分页查看审计；它不直接访问 SQLite，也不重新计算授权。关闭窗口只隐藏到托盘，服务发现当前会话缺少桌面端时会重新拉起。

会话锁定只由协作程序发起。服务不调用锁屏 API，也不把无法锁屏当作处置失败，只负责给出授权结论并记录结论变化。

导入项请求服务扫描所有本地已就绪卷（可移动盘、固定盘、光驱）的根目录，查找固定文件名 `anchor-guard.policy`。导入通道刻意不限于可移动盘：策略本身可能禁用 USB 大容量存储或刻录，介质类型不是安全边界，信任来自策略签名。服务完成校验和原子替换后写入审计事件，通知登录页重新枚举登录项；只有此时 Filter 才放行 Windows 系统登录方式。介质不存在、文件无效或导入失败时，登录页继续只显示导入项。

动态过滤系统 Credential Provider 是 Windows 登录界面的高风险集成点。该组件必须保持最小职责、禁止在登录界面执行策略解析或数据库访问，并以授权不明即拒绝为固定行为。

## 本地策略执行

`anchor-service` 以 Windows 服务运行，按固定周期重新观测受控设备并核对授权状态。各执行域只读取服务提供的当前策略，不保存自己的授权副本。

设备处置按差异下发：观测状态与策略期望一致的设备不执行控制命令，也不写审计事件；只有不一致的设备才会被处置并记录处置结果。设备状态或授权结论变化后，下一轮核对重新下发处置。核对周期和重试间隔决定响应延迟，不构成额外的授权状态。

### USB 存储

USB 管控只针对大容量存储设备，不影响键盘、鼠标、调试器和其他非存储外设。允许规则使用设备实例标识、VID/PID 和序列号匹配；未命中的 USB 存储设备禁用。观测范围包含被禁用设备，因此策略放开后能够恢复此前被禁用的设备。

设备接入、移除和处置结果各只写入一次审计：设备首次出现在观测中记录接入；被禁用后离开观测不再重复记录，重新接入时重新记录；仍处于启用状态的设备离开观测时记录移除。

### 网卡

策略明确允许的网卡类型或适配器保持启用，其他受控适配器禁用。服务只在适配器启用状态与策略不一致时下发处置，记录适配器标识、类型、启用状态和处置结果。网络连接内容不作为服务端上报数据处理。

### 刻录

刻录能力按策略中明确允许的光驱和状态执行。未授权时光驱被禁用，只有启用状态与策略不一致时才下发处置；服务记录光驱、介质摘要、关联进程摘要和处置结果。

### 登录界面只读通道

登录界面（开机登录页和锁屏页）期间，服务为可存储介质保留一条只读通道：可移动介质的 USB 大容量存储和刻录光驱都放行为启用状态，登录界面因此能读到介质上的策略文件而无法向外写入。只读属性来自系统级写入拒绝：可移动介质用 `Control\StorageDevicePolicies` 的 `WriteProtect`，CD/DVD 用 `RemovableStorageDevices` 的 `Deny_Write`。写入拒绝先落地再放行设备；没能落地时对应设备不放行，服务按设备处置失败记录并继续重试。

可移动介质写保护只对该开关开启之后挂载的介质生效，因此开关刚开启时，已经启用的可移动介质会被卸载并重新挂载一次。固定类型卷不参与这条通道：它们无法通过重新挂载变成只读，登录界面期间存在活动策略时保持禁用，没有策略依据时不处置。

登录界面的判断依据是登录界面进程是否在运行：它不依赖 IPC，服务重启后立即可用。远程桌面会话同样会让该判断成立，因此远程使用时不把它当作解锁状态的依据。

这条通道不来自策略，因此授权允许和授权拒绝时都维护：策略缺失、策略过期或运行状态异常时，登录界面仍然要能读到介质上的策略文件。授权拒绝时只跳过按策略下发的网卡处置，其余设备按上一条规则处理。

### 文件风险识别

文件监听只覆盖策略指定的目录和文件类型；`file_types` 为空表示扫描全部支持的类型。扫描器在文件稳定后提取支持格式的文本，匹配敏感词和正则规则，并把结果写入扫描索引。

每次扫描写一条审计事件：命中记为 `scan_hit`，未命中与提取失败记为 `scan_completed`，事件里带文件路径、哈希、命中规则、策略版本和扫描结果。操作者记录扫描发生时活动会话的登录用户名；用户态无法把文件写入者可靠归属到具体用户，因此该字段是会话级近似，取不到时写 `unknown`，会话标识记在事件进程字段。

文件扫描只做风险识别与审计，不阻止写入、不隔离、不删除文件。写入前阻断需要 Windows 内核文件系统 minifilter，不属于本设计的用户态 Rust 边界。

## 本地存储与审计

本地 SQLite 数据库存放在 Windows 受权限保护的程序数据目录，至少包含：

```text
policies       当前已导入策略及必要摘要
audit_events   追加式审计事件
scan_index     文件扫描索引和命中摘要
device_state   USB、网卡和刻录设备状态
runtime_state  最后可信时间、服务退出和授权恢复信息
```

每条审计事件包含事件 ID、设备 ID、用户或会话、时间、事件类型、资源摘要、策略版本、动作、结果、上一条哈希和当前哈希。当前哈希由事件规范化内容与上一条哈希计算，形成追加式 hash chain。

策略导入、验签失败、授权状态变化、登录或解锁拒绝、时间回拨、服务启动停止、会话协作程序异常、USB/网卡/刻录状态变化、文件扫描命中和审计校验均属于必须记录的事件。

周期核对不产生常态化审计：同一授权拒绝原因、同一设备处置失败原因和设备稳定状态都只记录一次。授权或设备状态恢复与策略一致后，再次异常会重新记录。

关键状态变化的顺序为：

```text
追加审计事件
  -> 提交审计事务
  -> 执行设备处置或更新派生状态
```

服务启动时校验审计 hash chain 和运行状态，并记录服务启动、审计校验结论和停止事件。校验失败、数据库不可读或运行状态无法恢复时进入登录拒绝状态，并在可写时追加相应异常事件。

审计查看集成在桌面端：审计页通过服务只读查询事件和整库 hash chain 结论，支持筛选和游标分页，不提供删除或修改入口。本期不提供独立导出 CLI；需要离线留存时，由管理员按内部流程复制 `C:\ProgramData\Anchor Guard\audit.db`，保留原始数据库及其校验结论。

hash chain 能发现已有记录被修改或中间删除；但没有服务端锚点或硬件信任根时，拥有本机管理员权限的人仍可能整体删除或重建本地材料。因此数据库缺失、校验失败、服务异常或无法读取数据库必须被视为审计材料不可信，而不是可被系统自动恢复的历史记录。

## 组件职责

目标 workspace 的 crate 边界如下：

- `anchor-core`：策略模型、签名验签、版本和有效期判断、审计事件与 hash chain。
- `anchor-ipc`：服务、登录组件和桌面端共用的本地管道协议。
- `anchor-store`：SQLite 迁移、事务、审计查询和本地状态持久化。
- `anchor-scan`：文件文本提取、敏感词和正则匹配、增量扫描判断。
- `anchor-system`：Named Pipe、会话锁定、策略介质与设备库存枚举、USB 存储、网卡和刻录 API 适配。
- `anchor-build`：`anchor-client/` 根目录的客户端构建与打包入口，不参与运行时。
- `anchor-service`：位于 `anchor-client/service/` 的 Windows 服务入口，组织策略导入、授权状态、设备执行和审计。
- `anchor-credential`：位于 `anchor-client/credential/` 的 Credential Provider 与动态 Filter 的 Rust COM DLL。
- `anchor-session`：位于 `anchor-client/session/` 的交互用户会话授权协作程序，收到拒绝时锁定该会话。
- `anchor-client/desktop`：Tauri 桌面端，负责托盘、策略预览导入和在线审计查看。

客户端、服务端和共享 crate 分属 `anchor-client`、`anchor-server`、`anchor-shared` 三个仓库；`anchor-client` 和 `anchor-server` 通过 `crates/shared` 子模块固定共享 crate 版本。客户端构建、桌面端构建和 MSI 打包统一由 `anchor-build` 编排。

`anchor-service` 是策略判断、授权状态和设备执行的唯一组织者。`anchor-credential` 只负责登录界面与受控 IPC；`anchor-system` 只封装 Windows 系统 API；其他 crate 不得平行保存或重新计算授权结论。

## 安装与使用

通用安装程序先写入服务端地址和端口，再安装 Windows 服务、Credential Provider 组件、会话协作程序和桌面端，并创建开始菜单快捷方式。客户端首次启动生成安装标识，注册后由管理员在服务端审批；批准后客户端从服务端获取验证公钥和签名策略。未获得有效策略的设备只显示策略导入入口。

管理员在服务端管理台编辑、签名和分配策略。离线兜底使用管理台导出的已签名策略包并放入本地卷根目录；用户在登录页选择导入策略，服务验证后恢复正常登录。策略到期后，`anchor-session` 锁定已登录会话，登录页再次仅保留导入策略入口。

用户即使拥有本机管理员权限，也不应被视为受到强制不可绕过的限制；系统的目标是默认锁定、阻断正常登录路径并留下可供归还审计的异常证据。

## 验证边界

策略签名、版本回退、有效期、时间回拨、审计 hash chain、U 盘包筛选和扫描规则必须有 Rust 自动测试。

Credential Provider、动态 Filter、登录页导入、策略到期后的会话锁定、桌面端托盘与单实例、在线审计、快速用户切换、重启恢复、服务不可用、U 盘导入失败及各 Windows 设备控制 API 必须在 Windows 10 虚拟机和专用测试机上验证。登录组件不得直接部署到唯一可用的管理员电脑或生产笔记本进行首次验证。
